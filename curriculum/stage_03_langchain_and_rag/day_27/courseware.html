Memory 记忆机制：滑动窗口、摘要压缩与 SQLite 多会话隔离

企业需求驱动（Issue #027）：告别大模型“金鱼脑”与多租户串台事故，构建可持久化、可扩展的企业级记忆引擎

🎙️ 讲师旁白（企业痛点导入）：
大模型本身是无状态（Stateless）的——每次 API 调用它都不记得上一秒说过什么。为了实现多轮对话，我们必须由应用层维护历史消息。但如果直接把所有历史塞进 Prompt，很快就会触发上下文长度上限与高昂的 Token 账单；如果多个部门共用一个内存列表，更会发生严重的数据串台泄密。今天我们就用 WindowMemory、SummaryMemory 和 SQLiteChatMessageHistory 彻底解决这三大难题！

一、多会话记忆隔离与策略路由架构

通过 RunnableWithMessageHistory，每次调用都会根据 session_id 自动隔离加载历史、应用记忆压缩策略，并在生成回复后自动落库：

sequenceDiagram actor UserA as 租户 A (tenant-fin) participant Wrapper as RunnableWithMessageHistory participant Strategy as Window / Summary Memory participant DB as SQLiteChatMessageHistory participant Chain as 业务问答链 UserA->>Wrapper: invoke(input, config={"configurable": {"session_id": "tenant-fin"}}) Wrapper->>DB: 按 session_id="tenant-fin" 读取历史 DB-->>Wrapper: 仅返回租户 A 的消息列表 Wrapper->>Strategy: 裁剪窗口或生成早期摘要 Strategy-->>Wrapper: 精简后的 context_messages Wrapper->>Chain: 调用 runnable({"input": ..., "history": context_messages}) Chain-->>Wrapper: 返回 ai_reply Wrapper->>DB: 写入 user 与 assistant 消息 Wrapper-->>UserA: 返回最终回复

二、三大核心记忆策略对比

策略 / 存储组件 核心机制 Token 成本 适用企业场景
InMemoryChatMessageHistory 进程内存列表存储 随轮次线性增长 本地开发、单元测试、一次性脚本
SQLiteChatMessageHistory SQLite 落盘 + session_id 索引隔离 持久化底层仓储 多租户 Web 服务、进程重启恢复
WindowMemory(k) 保留 System Prompt + 最近 k 轮（2k 条） 固定可控上限 高频短对话、客服问答、工具调用
SummaryMemory 近期原样保留 + 早期历史压缩为摘要 低且可保留长程事实 长周期项目顾问、复杂需求梳理

三、核心代码实战：`RunnableWithMessageHistory`

from pathlib import Path
from zhishu_agent.memory import (
    RunnableWithMessageHistory,
    SQLiteChatMessageHistory,
    WindowMemory,
)

db_path = Path("zhishu_memory.db")
chain = RunnableWithMessageHistory(
    runnable=lambda payload: f"[{payload['session_id']}] 上下文 {len(payload['history'])} 条 -> {payload['input']}",
    get_session_history=lambda sid: SQLiteChatMessageHistory(session_id=sid, db_path=db_path),
    memory_strategy=WindowMemory(k=2, keep_system=True),
)

reply = chain.invoke("差旅住宿标准是多少？", config={"configurable": {"session_id": "tenant-fin"}})
print(reply)

四、课堂自测与思考

思考题：为什么 WindowMemory 不能直接对全部消息做 messages[-2*k:]？

点击查看参考解析

因为第 0 条消息通常是 system 角色的系统提示词（System Prompt），定义了智能体的身份、合规红线与输出格式。如果直接从末尾切片，系统提示词会在第 k+1 轮被挤出上下文窗口，导致智能体失忆或越权。因此必须先分离 system 消息，仅对用户/助手对话做滑动窗口裁剪。
