一、AST 静态代码审计流水线架构

不同于脆弱的正则表达式，ast.parse() 能将 Python 源码解析为精确的抽象语法树（Abstract Syntax Tree），从而零误报地识别语法结构：

flowchart TD DIR["迭代目录 project_iterations/day_XX"] --> WALK["递归扫描 *.py (跳过 __pycache__/.venv)"] WALK --> PARSE["ast.parse() 构建语法树"] PARSE -->|"SyntaxError"| ERR_SYN["记录 syntax-error (Error 阻断)"] PARSE -->|"成功"| AST["ast.walk(tree) 遍历节点"] AST --> DOC["Docstring 覆盖率 (Module / Class / Func)"] AST --> HINT["Type Hints 覆盖率 (参数豁免 self/cls & 返回值)"] AST --> CALL["ast.Call 拦截 eval() / exec()"] AST --> KEY["ast.Constant 扫描 sk-... 硬编码密钥"] DOC --> RPT["ProjectAuditReport & format_summary()"] HINT --> RPT CALL --> RPT KEY --> RPT ERR_SYN --> RPT

二、核心审计规则与门禁分级

规则 ID AST 检测目标 严重级别 工程意义与修复建议
missing-*-docstring Module / ast.ClassDef / ast.FunctionDef warning 保证团队协作可读性与 API 文档自动生成能力
missing-type-hints 函数参数（豁免 self/cls）与 returns warning 配合 mypy/pyright 提前暴露类型契约错误
forbidden-dynamic-exec ast.Call 调用 eval / exec error（阻断） 严防代码注入（RCE）高危漏洞，改用安全解析器
hardcoded-api-key 字符串常量匹配 sk-[A-Za-z0-9_-]{10,} error（阻断） 防止敏感凭证泄漏至 Git，必须通过环境变量注入

四、课后思考与阶段复盘

思考 1：为什么我们在检查函数调用时使用 isinstance(node, ast.Call) 而不是直接用正则搜 r"eval\("？

点击查看解析

如果源码的注释或帮助文档里写了 # 请勿使用 eval()，纯正则表达式会产生误报（False Positive）；而基于 ast.Call 节点检测只会匹配真实的可执行调用语法，实现零误报。

思考 2：在 Project 2（Stage 3）中，Ragas 评估体系与 AST 代码审计各自守护了系统的哪道防线？

点击查看解析

Ragas 评估守护的是 AI 应用的业务效果防线（检索召回、排序精度、模型幻觉与相关性）；AST 代码审计守护的是软件工程的代码质量与安全防线（类型契约、文档规范、零密钥泄漏与零危险动态执行）。两者结合，才构成企业级 AI 工程交付的完整闭环。
