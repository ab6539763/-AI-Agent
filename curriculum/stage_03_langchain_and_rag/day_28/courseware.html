一、RAG 文档接入与切分流水线（Pipeline）

从原始企业文件到可入库检索的语义切片，数据流向如下：

二、核心组件与切分策略对比

1. 统一文档模型与多格式 Loader

组件名称适用场景自动注入的元数据（Metadata）
Document所有 Loader 与 Splitter 的标准输入输出自定义字典（实例间严格浅拷贝隔离）
TextLoader纯文本规范、日志文件（.txt）source, file_name, file_type, loader
MarkdownLoader研发手册、PRD 文档（.md）自动提取首个 # 一级标题为 title
CSVLoader客服 FAQ、产品目录表（.csv）逐行转为 Document，记录 row 行号与 source_column

2. 三大 TextSplitter 原理与选型

切分器核心机制工程优势
CharacterTextSplitter按单一分隔符拆分后按窗口合并逻辑简单，适合格式高度规整的日志或行记录
RecursiveCharacterTextSplitter按 ["\n\n", "\n", "。", " ", ""] 层级递归切分优先保留段落与中文完整句意，仅在超长时逐级降级
MarkdownHeaderTextSplitter按 # / ## / ### 标题状态机切分保留章节层级到 metadata，且自动忽略代码块内 # 注释

3. 核心代码示例

from zhishu_agent.document_loader import (
    MarkdownLoader,
    MarkdownHeaderTextSplitter,
    RecursiveCharacterTextSplitter,
)

docs = MarkdownLoader("handbook.md").load()
header_chunks = MarkdownHeaderTextSplitter().split_documents(docs)

recursive_splitter = RecursiveCharacterTextSplitter(
    chunk_size=300,
    chunk_overlap=40,
    separators=["\n\n", "\n", "。", " ", ""],
)
final_chunks = recursive_splitter.split_documents(header_chunks)

点击查看：为什么建议先用 MarkdownHeaderTextSplitter，再套一层 RecursiveCharacterTextSplitter？

这种“两阶段切分”是企业级 RAG 的最佳实践：先按 Markdown 标题把整篇文档拆成带章节元数据（Header 1/2/3）的语义块，如果某个章节本身依然超过向量模型的 Token 上限，再用 RecursiveCharacterTextSplitter.split_documents() 二次切分，既控制了长度，又让每个子片段都携带完整的章节归属信息！
