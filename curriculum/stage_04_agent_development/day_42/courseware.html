在企业级智能体落地中，单次同步调用往往无法应对长耗时任务与高风险决策。今天我们将为智枢平台打造四大生产级基础设施：SQLiteCheckpointer（按 thread_id 持久化断点）、interrupt_before / resume（人工审稿门禁）、ParallelSectionRunner（多线程并发写章）以及 RetryPolicy（节点级指数退避重试）。

一、Writing Agent 全链路状态机架构

Writing Agent 将长文创作拆解为“大纲生成 → 人工审批拦截 → 并发章节撰写 → 终稿汇总润色”四段式状态机：

flowchart TD START(["START: 输入 topic"]) --> OUTLINE["Outline: generate_outline 生成大纲"] OUTLINE -->|"SQLiteCheckpointer 保存快照"| INT["[Interrupt/Approve] interrupt_before 人工审批暂停"] INT -->|"resume(thread_id, updated_state)"| CHECK{"approved == True ?"} CHECK -->|"False (打回重写)"| OUTLINE CHECK -->|"True (通过)"| PAR["Parallel Chapters: ParallelSectionRunner (ThreadPoolExecutor + RetryPolicy)"] PAR --> POLISH["Polish: final_polish 汇总润色"] POLISH --> END_NODE(["END: 输出 final_article"])

二、四大核心机制与工程设计

核心组件 解决的生产痛点 关键 API / 实现机制
SQLiteCheckpointer 进程崩溃或长耗时等待时状态丢失、多用户上下文串扰 按 thread_id 隔离存储 state_json、next_node、status，支持 get_latest() 与 get_history()
interrupt_before & resume() 高风险节点需人工把关或修订中间产物（Human-in-the-loop） 命中拦截点写入 status="interrupted"；恢复时合并 updated_state 并跳过首轮重复拦截
ParallelSectionRunner 多章节串行生成延迟高，且并发返回乱序 ThreadPoolExecutor 并发执行，按原始大纲 index 确定性重排汇总
RetryPolicy 大模型 API 偶发超时、限流导致整张图失败 配置 max_retries、initial_delay_s、backoff_factor 与 retry_on 异常白名单

三、核心代码实战：人工拦截与跨实例恢复

from pathlib import Path
from zhishu_agent import RetryPolicy, SQLiteCheckpointer, build_writing_agent_graph

cp = SQLiteCheckpointer(Path("checkpoints.db"))
app = build_writing_agent_graph(
    checkpointer=cp,
    max_workers=4,
    node_retry_policy=RetryPolicy(max_retries=2, initial_delay_s=0.01),
)

# 1. 启动任务并在 human_approval 前自动暂停
paused = app.invoke({"topic": "企业级 AI Agent 治理"}, thread_id="book-001")
assert paused.status == "interrupted"

# 2. 人工修改大纲并注入 approved=True 恢复执行
completed = app.resume(
    "book-001",
    updated_state={
        "approved": True,
        "outline": [*paused.state["outline"], "第四章：灰度发布与合规审计"],
        "human_feedback": "大纲已审阅通过",
    },
)
print(completed.state["final_article"])

四、课后思考与自检清单

点击展开：为什么 resume() 恢复执行时必须跳过首轮 interrupt_before 检查？

当图在节点 human_approval 前暂停时，检查点记录的 next_node 正是 human_approval。如果不跳过首轮拦截，调用 resume() 后图会在同一节点再次触发暂停，导致无限死锁。因此引擎通过 skip_interrupt_on_first=True 放行当前已获批的断点节点。

点击展开：为什么 ParallelSectionRunner 需要按原始 index 重排结果？

多线程并发执行时，各章节耗时受内容复杂度与重试次数影响，完成顺序通常与大纲顺序不一致。按 index 映射收集结果并按 range(len(sections)) 输出，才能保证终稿章节顺序 100% 确定。
