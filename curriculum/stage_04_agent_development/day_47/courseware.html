实战场景：Text-to-SQL 企业数据分析智能体

企业需求驱动（Issue #047）：构建 Schema 自省、自然语言转 SQL、只读安全护栏与中文商业洞察闭环

🎙️ 讲师旁白（让业务人员用自然语言直接“对话数据库”）：
在企业日常运营中，“各大区目标达成率如何？”、“Top 5 畅销产品是谁？”这类临时取数需求非常高频。但直接把数据库交给大模型极其危险——既可能因幻觉写错列名，更可能被恶意诱导执行 DROP TABLE 或 DELETE。今天我们为智枢平台构建 SalesDatabase（SQLite 销售业务库）、validate_readonly_sql()（只读 SQL 硬护栏）与 TextToSQLAgent（自然语言问数与中文商业洞察引擎）。

一、Text-to-SQL 端到端数据流架构

每次自然语言问数均严格遵循“提问 → Schema 自省 → SQL 生成 → 只读安全护栏 → SQLite 执行 → 商业洞察”六步流水线：

flowchart LR Q(["Question: 自然语言提问"]) --> SCHEMA["Schema: introspect_schema()"] SCHEMA --> GEN["SQL: generate_sql()"] GEN --> GUARD{"AST/Keyword Guard: validate_readonly_sql()"} GUARD -->|"含 DROP/DELETE/;/PRAGMA"| BLOCK(["拦截: SQLSecurityError"]) GUARD -->|"合法单条 SELECT"| DB[("SQLite: SalesDatabase")] DB --> INSIGHT(["Insight: 中文商业洞察"])

二、三大核心模块与工程设计

核心组件 解决的业务与安全痛点 关键设计要点
SalesDatabase 大模型缺乏真实表结构上下文，易产生字段幻觉 内置 regions、products、orders 三张关联表，开启外键约束；通过 introspect_schema() 提取真实 DDL 与行数。
validate_readonly_sql 提示词软约束易被越狱，存在删库/篡改/堆叠注入风险 严格限制首词为 SELECT，拦截分号 ;、注释符 --//* 以及 DROP/DELETE/UPDATE/INSERT/ALTER/PRAGMA。
TextToSQLAgent 仅有原始二维表格难以直接辅助管理层决策 串联 Schema 自省、NL 转 SQL（支持外部 llm_fn 或内置规则）、安全执行与 summarize_insight() 中文洞察摘要。

三、核心代码实战示例

1. 初始化销售库并运行 TextToSQLAgent 多表关联分析

from zhishu_agent import SalesDatabase, TextToSQLAgent

with SalesDatabase(":memory:") as db:
    db.initialize_and_seed()
    agent = TextToSQLAgent(db=db)

    res = agent.ask("各大区已完成订单的实际销售额与目标达成率是多少？")
    print("生成 SQL:", res.generated_sql)
    print("状态:", res.status, "| 返回行数:", len(res.rows))
    print("商业洞察:", res.insight)
