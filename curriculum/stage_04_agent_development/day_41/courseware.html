一、为什么需要 LangGraph？核心概念与状态图拓扑

一个标准的 StateGraph 由三大要素构成：全局 State（含 Annotated 归约器）、Node（节点函数）、Edge / Conditional Edge（普通边与条件边）。

stateDiagram-v2 [*] --> risk_assess risk_assess --> auto_approve : low_risk (<= 1000元) risk_assess --> human_review : high_risk (超额或高危操作) auto_approve --> execute_action human_review --> execute_action : approved human_review --> reject_action : rejected execute_action --> [*] reject_action --> [*]

二、StateGraph 核心 API 速查表

API / 符号 作用说明 企业工程注意点
START / END 状态图虚拟入口与终止哨兵节点 编译前必须存在至少一条从 START 出发的边
add_node(name, fn) 注册状态处理节点，接收 state 并返回增量字典 节点函数保持纯函数风格，仅返回需更新的字段
add_conditional_edges() 根据路由函数返回值动态决定下一跳节点 建议显式传入 path_map，便于 to_mermaid() 静态导出
Annotated[list, operator.add] 声明字段归约器（Reducer），增量追加而非覆盖 非常适合累积 messages 对话历史与 audit_log 审计日志
compile() / stream() 校验拓扑并流式执行，支持 recursion_limit 所有循环图必须配合业务上限 + recursion_limit 双重守卫

三、核心代码实战：ReAct 循环图与人工审批流

from zhishu_agent import build_approval_graph, build_react_graph

# 1. ReAct 工具调用循环图：reason -> tools -> reason -> END
react_app = build_react_graph(max_iterations=5)
print(react_app.to_mermaid())

for step in react_app.stream({"query": "请帮我计算 25 * 4", "messages": [], "iteration": 0}):
    print(step)

# 2. 高风险操作/费用报销人工审批流
approval_app = build_approval_graph(auto_approve_limit=1000.0)
res = approval_app.invoke({
    "request_id": "REQ-2026-01",
    "action_type": "expense",
    "amount": 3200.0,
    "human_decision": True,
    "audit_log": [],
})
print(res["approval_status"], res["execution_result"])

四、课后思考与工程防坑

思考 1：为什么 ReAct 状态图在状态设计上推荐使用 Annotated[list, operator.add] 来管理 messages？

点击查看解析

如果每次节点都必须手动拷贝并拼接完整历史列表，代码既冗余又容易在并发或分支节点中丢失消息。使用 Annotated[list, operator.add] 后，节点只需返回本轮新增的 {"messages": [new_msg]}，图引擎会自动将新消息安全追加到全局状态中。

思考 2：如果 human_review 节点既没有配置 approver_fn，请求中也未传入 human_decision，应该默认通过还是驳回？

点击查看解析

必须默认驳回（Fail-Closed）！在企业安全架构中，涉及生产数据库变更、大额资金划拨的高风险分支，任何未获得明确人工授权的情况都必须拒绝执行并写入 audit_log。
