里程碑项目 3（Part 2）：多 Agent 智能办公助手全栈交付

企业需求驱动（Issue #049）：FastAPI 后端 + SQLite 检查点持久化 + Human-in-the-Loop（HITL）人工审批前端工作台

🎙️ 讲师旁白（让人类站在高危动作的最后一道防线）：
在企业级办公自动化中，“查制度”可以全自动放行，但“发全员邮件、批报销、订高管会议室”必须经过人类审批。今天我们将把多 Agent 编排引擎接入 FastAPI 与 Web 审批工作台，实现“执行 → 中断挂起（awaiting_approval）→ 人工 Approve/Reject → 检查点恢复（resume）”的全栈闭环！

通过 OfficeCheckpointer（SQLite）将挂起线程状态落盘，前端通过 thread_id 展示审批卡片并调用 /api/v1/office/resume 恢复执行：

sequenceDiagram autonumber actor User as 企业员工 / 审批人 participant UI as Web UI (index.html) participant API as FastAPI (office_web_app.py) participant Sup as OfficeOrchestrator participant DB as SQLite Checkpointer User->>UI: 提交办公指令（如：发送全员邮件） UI->>API: POST /api/v1/office/run API->>Sup: run(task) Sup->>DB: 保存挂起状态 (awaiting_approval) API-->>UI: 返回 thread_id + pending_action UI-->>User: 渲染 HITL 审批卡片 (Approve / Reject) User->>UI: 点击 Approve 或 Reject UI->>API: POST /api/v1/office/resume API->>DB: load(thread_id) 并校验状态机 Sup->>DB: 更新终态 (completed / rejected) API-->>UI: 返回最终流转轨迹与执行回执

二、FastAPI 核心接口契约

方法与路径 核心职责 关键响应 / 状态码
GET / 托管 frontend/index.html 多 Agent 审批工作台 200 HTMLResponse
POST /api/v1/office/run 启动 Supervisor + Worker 编排，低风险直接完成，高风险触发中断 200 ThreadState（completed / awaiting_approval），空任务 400
POST /api/v1/office/resume 接收 approved、comment 与可选 edited_payload 恢复执行 200 ThreadState（completed / rejected），不存在 404，重复审批 409
GET /api/v1/office/threads/{thread_id} 查询指定线程的完整流转轨迹与待审批载荷 200 ThreadState / 404

三、随堂思考与课后实战

思考题：为什么 POST /api/v1/office/resume 在线程已完成后再次调用必须返回 409 Conflict？

点击查看参考解析

审批动作（如发送全员邮件、财务打款）具有不可逆的外部副作用。如果前端因网络抖动或用户连击导致同一 thread_id 被重复提交 resume，服务端通过状态机守卫（仅允许 status == "awaiting_approval" 进入恢复逻辑，否则抛出 InvalidThreadStateError 映射为 HTTP 409）即可保证严格幂等与资金/消息安全。
