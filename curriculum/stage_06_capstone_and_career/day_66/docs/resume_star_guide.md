# Day 66 实战指南：三类人群 STAR 法则简历改写对照表

> **核心心法**：面试官平均每份简历只看 **15~30 秒**。不要写“我做了什么功能”，而要写**“在什么业务痛点下（S/T），用什么硬核技术方案（A），拿到了多少可验证的量化结果（R）”**。

---

## 一、传统后端/Java/前端转行者（突出工程化迁移能力 + AI 落地闭环）

### ❌ 改写前（常见扣分写法）
- 参与公司 AI 智能体平台开发，使用 Python 和 FastAPI 写了几个接口，接入了大模型和知识库，功能上线后运行稳定。

**问题诊断**：
1. 动词偏弱（“参与”、“写了几个接口”）；
2. 缺乏具体技术深度（没写 SSE、没写 RAG 融合策略、没写 HITL 或测试）；
3. 零量化指标（“运行稳定”无法衡量）。

### ✅ 改写后（STAR 高亮版）
- **针对企业内部财报问答延迟高且高风险指令缺乏人工复核的痛点（S）**，**主导构建智枢智能体全栈交互网关与审批闭环（T）**；**基于 FastAPI + `ReadableStream` SSE 实现流式推理推送，引入 SQLite 状态机与 PII 正则脱敏实现 `pending -> approved/rejected` 幂等人工审批（A）**，**最终实现高风险动作 100% 强制拦截复核、重复审批拦截率 100%，首字响应延迟降至 280ms，并通过 25 项 `pytest` 自动化回归（R）**。

---

## 二、计算机/人工智能应届生（突出架构理解 + 评测基线 + 可复现工程能力）

### ❌ 改写前（常见扣分写法）
- 毕业设计做了一个基于 RAG 的企业文档问答系统，使用向量数据库检索文档后交给大模型回答，准确率比较高。

**问题诊断**：
1. 像“课程大作业”，缺少真实工程痛点（如长尾词/股票代码漏召回）；
2. 缺少对比基线与评测指标（“准确率比较高”没有说服力）。

### ✅ 改写后（STAR 高亮版）
- **针对纯 Dense Vector 检索在财报股票代码与专有财务术语上召回率低的问题（S）**，**独立负责智枢混合 RAG 检索引擎研发与评测体系建设（T）**；**设计 BM25 稀疏检索 + FAISS 向量检索双路召回，结合 RRF（倒数秩融合）与 Cross-Encoder Rerank 精排，并强制输出段落级引用溯源（A）**，**最终在 200 条财报测试集上将 Top-5 召回率从 71% 提升至 92%（+21%），P95 检索延迟控制在 165ms 以内（R）**。

## 三、产品经理 / AI PM（突出业务拆解 + 合规边界 + ROI 量化收益）

### ❌ 改写前（常见扣分写法）
- 负责智枢 AI 智能体产品规划，设计了多 Agent 协作和人工审批功能，协调研发团队按时上线，提升了业务效率。

**问题诊断**：
1. 缺少 AI 产品特有的“边界意识”（幻觉控制、越权风险、PII 合规）；
2. 没有体现数据驱动的验收标准（如命中率、人工复核率、耗时下降比例）。

### ✅ 改写后（STAR 高亮版）
- **针对金融合规场景下大模型自主调用工具存在资金划拨越权与敏感数据泄露风险（S）**，**主导《智枢财报与合规分析台》PRD 定义与 HITL 人机协同闭环设计（T）**；**拆解“低风险自动流转、高风险强制挂起”两级策略，推动研发落地 PII 入库脱敏、SSE 思考态可观测及引用证据溯源面板（A）**，**最终使合规审核人效提升 3.2 倍，单份财报核验耗时由 45 分钟缩短至 8 分钟，上线后零安全越权事故（R）**。

## 四、GitHub 作品集 README 避坑自查清单

| 检查维度 | 权重 | 优秀标准 |
| --- | --- | --- |
| **系统架构图** | 20 分 | 首页直接展示 Mermaid 流程图或清晰架构图，一眼看懂数据流 |
| **Quickstart** | 20 分 | 3 条以内命令可本地跑通（含 `pip install`、`uvicorn`、`pytest`） |
| **API 文档** | 20 分 | 明确核心 Endpoint、请求体 JSON 与 SSE/响应格式 |
| **评测基线** | 20 分 | 有定量对比表（如 Pure Vector vs Hybrid RRF 的 Recall@5 与 Latency） |
| **Demo GIF/截图** | 10 分 | 15 秒动图或界面截图，证明项目“真能跑、有交互” |
| **License** | 10 分 | 清晰的 MIT / Apache-2.0 协议声明 |
