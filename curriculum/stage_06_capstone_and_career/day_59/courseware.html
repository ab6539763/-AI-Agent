一、Capstone Day 1 知识库构建流水线

企业财务与合规语料通常混合了非结构化制度文档（.md）与结构化台账（.csv）。为了支持后续高精度混合检索与权限/财年过滤，我们在入库阶段强制完成：目录扫描 → 元数据提取 → 语义切片 → JSON 审计快照 & SQLite 幂等持久化。

flowchart LR CORPUS["企业语料 (.md / .csv)"] --> SCAN["ingest_directory()"] SCAN --> META["extract_metadata(): department / fiscal_year / doc_type"] META --> MD["parse_markdown(): 标题分节 + 滑动窗口"] META --> CSV["parse_csv(): 批次行聚合保留表头"] MD --> CHUNK["KBChunk (确定性 chunk_id)"] CSV --> CHUNK CHUNK --> JSON["save_json_index(): kb_index.json"] CHUNK --> SQLITE["save_sqlite_index(): kb_index.sqlite"] SQLITE --> QUERY["query_sqlite(): 元数据过滤检索"]

二、核心设计要点与元数据规范

字段 / 模块 设计规范 工程价值
department 优先解析 Frontmatter，其次匹配文件名关键词，最后回退正文 避免财务台账因某行出现 compliance 字样而被误分类
fiscal_year 统一标准化为 FY2025 / FY2026 格式 支持按财年精准隔离历史制度与当期财报，防止跨期幻觉
doc_type 区分 financial_report、compliance_policy、financial_ledger 为后续多路召回与重排提供文档类型权重依据
chunk_id sha256(source_file:chunk_index:content_hash)[:20] 配合 SQLite INSERT OR REPLACE 实现 100% 幂等重建

三、核心代码速览（CapstoneKBInitializer）

from zhishu_agent import CapstoneKBInitializer

initializer = CapstoneKBInitializer(chunk_size=300, chunk_overlap=40)
chunks, stats = initializer.build_and_persist(
    input_dir="data/corpus",
    json_path="artifacts/kb_index.json",
    sqlite_path="artifacts/kb_index.sqlite",
)

hits = initializer.query_sqlite(
    db_path="artifacts/kb_index.sqlite",
    department="compliance",
    fiscal_year="FY2026",
)
print(f"构建切片: {stats.total_chunks}, 合规制度命中: {len(hits)}")

四、课堂思考与自测

思考题：为什么在 Capstone Day 1 我们先将切片结果持久化到 JSON 与 SQLite，而不是直接写入向量数据库？

点击查看参考解析

先落盘 JSON 快照与 SQLite 关系索引，可以在不消耗 Embedding API/GPU 成本的情况下，快速审计切片边界、验证 department/fiscal_year/doc_type 元数据提取准确率，并支持确定性单元测试。Day 60 只需遍历 SQLite 中的 kb_chunks 即可批量生成向量写入 Qdrant/Milvus，实现解析层与向量检索层的解耦。
